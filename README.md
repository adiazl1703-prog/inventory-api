# Inventory API

[English](#english) | [Español](#español)

---

## English

REST API to manage an organization's computer equipment inventory: the lifecycle of IT assets, employees, and a permanent log of assignments and returns.

**Stack:** NestJS 12, PostgreSQL 17, Prisma 7, class-validator, class-transformer, Jest, Docker and Docker Compose.

### Prerequisites

- Node.js 24 and npm
- Docker with Docker Compose

### Installation

```bash
git clone <repository-url>
cd inventory-api
npm install
cp .env.example .env    # PowerShell: Copy-Item .env.example .env
```

Edit `.env` and replace `change_me` with your own password in **both** `POSTGRES_PASSWORD` and `DATABASE_URL`. If the password contains special characters, URL-encode it in `DATABASE_URL`.

| Variable | Description |
| --- | --- |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Credentials for the PostgreSQL container |
| `POSTGRES_PORT` | Host port published for PostgreSQL (default `5432`) |
| `DATABASE_URL` | Connection string used by Prisma and by the API when it runs on the host |
| `PORT` | API port (default `3000`) |

### Running the application

**Option A: everything in Docker.** Migrations are applied automatically when the API container starts.

```bash
docker compose up -d --build
```

**Option B: database in Docker, API on the host** (recommended for development).

```bash
docker compose up -d db
npm run prisma:deploy
npm run start:dev
```

Once running:

- API: <http://localhost:3000/api/v1>
- Swagger UI (bilingual): <http://localhost:3000/docs>

### Database migrations

| Command | Use |
| --- | --- |
| `npm run prisma:deploy` | Apply pending migrations (setup, CI, production) |
| `npm run prisma:migrate -- --name <name>` | Create and apply a new migration after editing `prisma/schema.prisma` (development) |
| `npm run prisma:generate` | Regenerate the Prisma client (also runs before build and tests) |

The initial migration contains two rules written by hand that are not expressed in `schema.prisma`, so keep them in mind if you recreate migrations from scratch:

- A partial unique index allowing only one open assignment per equipment.
- A check constraint ensuring `returned_at` is not earlier than `assigned_at`.

### Tests

```bash
npm test             # Unit tests
npm run test:cov     # Unit tests with coverage
npm run test:e2e     # End-to-end tests (requires the database running and migrated)
```

The end-to-end suite writes test records to the database in `DATABASE_URL` and does not delete them, because assignment history is permanent. Do not run it against a production database.

### Endpoints

All routes use the `/api/v1` prefix.

| Method | Route | Description |
| --- | --- | --- |
| POST | `/equipments` | Register equipment |
| GET | `/equipments?location=&status=&page=&limit=` | List equipment, filtered by location and status |
| GET | `/equipments/:id` | Get equipment by ID |
| PATCH | `/equipments/:id` | Update equipment |
| PATCH | `/equipments/:id/decommission` | Decommission equipment |
| GET | `/equipments/serial/:serialNumber/assignments` | Complete assignment history of a serial number |
| POST | `/employees` | Register an employee |
| GET | `/employees?page=&limit=` | List employees |
| GET | `/employees/:id` | Get employee by ID |
| GET | `/employees/:id/equipments` | Equipment currently assigned to an employee |
| POST | `/assignments` | Assign equipment to an employee |
| GET | `/assignments/:id` | Get assignment by ID |
| PATCH | `/assignments/:id/return` | Register a return |

### Business rules

- `location` accepts only `Bogota` or `Cartagena`, for both equipment and employees.
- `status` accepts `available`, `assigned`, `in_repair` or `decommissioned`.
- Serial numbers, ID documents and emails are unique. Emails are stored in lowercase.
- Status can be set manually only to `available` or `in_repair`. The `assigned` status comes from assignments and `decommissioned` from the decommission endpoint.
- Only `available` equipment can be assigned. Each unit can have only one open assignment, even under concurrent requests.
- Registering a return closes the assignment and sets the equipment back to `available`.
- Assigned equipment must be returned before decommissioning or changing its status.
- Decommissioned equipment cannot be modified or assigned. Its record and history are kept.
- Assignment timestamps are generated by the server. The API has no way to delete assignments, and foreign keys prevent deleting equipment or employees with history.

### Error responses

| Code | Meaning |
| --- | --- |
| 400 | Invalid data, unknown fields or malformed ID |
| 404 | Record not found |
| 409 | Duplicate unique value or action not allowed in the current status |

- Docker con Docker Compose

```bash
npm test             # Pruebas unitarias

```

Las pruebas de extremo a extremo escriben registros de prueba en la base de datos de `DATABASE_URL` y no los eliminan, porque el historial de asignaciones es permanente. No las ejecute contra una base de datos de producción.

### Endpoints

Todas las rutas usan el prefijo `/api/v1`.

| Método | Ruta | Descripción |
| --- | --- | --- |
| POST | `/equipments` | Registrar un equipo |
| GET | `/equipments?location=&status=&page=&limit=` | Listar equipos, con filtro por ubicación y estado |
| GET | `/equipments/:id` | Consultar un equipo por ID |
| PATCH | `/equipments/:id` | Actualizar un equipo |
| PATCH | `/equipments/:id/decommission` | Dar de baja un equipo |
| GET | `/equipments/serial/:serialNumber/assignments` | Historial completo de asignaciones de un número de serie |
| POST | `/employees` | Registrar un empleado |
| GET | `/employees?page=&limit=` | Listar empleados |
| GET | `/employees/:id` | Consultar un empleado por ID |
| GET | `/employees/:id/equipments` | Equipos asignados actualmente a un empleado |
| POST | `/assignments` | Asignar un equipo a un empleado |
| GET | `/assignments/:id` | Consultar una asignación por ID |
| PATCH | `/assignments/:id/return` | Registrar una devolución |

### Reglas de negocio

- `location` solo acepta `Bogota` o `Cartagena`, tanto para equipos como para empleados.
- `status` acepta `available`, `assigned`, `in_repair` o `decommissioned`.
- Los números de serie, documentos de identidad y correos son únicos. Los correos se guardan en minúsculas.
- El estado solo puede fijarse manualmente en `available` o `in_repair`. El estado `assigned` proviene de las asignaciones y `decommissioned` del endpoint de baja.
- Solo se pueden asignar equipos en estado `available`. Cada unidad puede tener una sola asignación abierta, incluso con solicitudes simultáneas.
- Al registrar una devolución se cierra la asignación y el equipo vuelve a `available`.
- Un equipo asignado debe devolverse antes de darlo de baja o de cambiar su estado.
- Un equipo dado de baja no se puede modificar ni asignar. Su registro e historial se conservan.
- El servidor genera las fechas y horas de las asignaciones. La API no permite eliminar asignaciones, y las llaves foráneas impiden eliminar equipos o empleados con historial.

| 404 | Registro no encontrado |
| 409 | Valor único duplicado o acción no permitida en el estado actual |
